# Not built: how the remaining bonus items would be done

Three of the five bonus items are built (lost-update protection, Make it an Issue from a Rock or To-Do, and the [1,000-companies note](SCALING.md)). These two were designed but deliberately not built before the deadline. The full designs are in [DEVELOPMENT_PLAN.md](../DEVELOPMENT_PLAN.md), sections 3.18 and 3.16; this is the short version.

## Activity log (audit trail): about 5.5 hours

**Goal:** a durable, append-only history of every change to every data table (who, what, when, before and after), searchable by Admins, without slowing down or risking the app's own writes.

1. **Capture with one generic trigger on every data table**, not in app code, so no write path can forget to log (the API, the seed, a manual `psql` fix). Each write transaction first sets `eos.actor_id`, `eos.request_id` and `eos.source` with `set_config(..., true)`; the trigger reads them and writes one row per change, with the before and after values as JSON. Bookkeeping-only updates (the cache version bump, `version` counters) are skipped.
2. **Hand-off through a transactional outbox** in the main database: the trigger only inserts into `activity_outbox`, in the same transaction as the change, so an event exists if and only if the change committed. No network call happens inside a user's transaction.
3. **A background worker** (same image, `python -m app.activity`) drains the outbox in batches with `FOR UPDATE SKIP LOCKED`, writes the events into a **separate database, `eos_activity`**, and deletes what it moved. If it is down, the API is unaffected and the outbox grows; `/healthz` warns after 5 minutes of backlog.
4. **Least privilege:** `eos_app` can't touch the outbox directly (the trigger is `SECURITY DEFINER`); the worker's writer role can only `INSERT` and `SELECT` in `eos_activity`, so the log is append-only even for the code that writes it.
5. **Reads:** `GET /activity` (Admins only; already specified in [API_CONTRACTS.md](API_CONTRACTS.md), section 11a) with filters by team, table, operation, actor, date range, row and request, keyset pagination, and Postgres full-text search (`websearch_to_tsquery`).
6. **Admin page** `/admin/activity`: events grouped by transaction like a git commit, each row change as an expandable `-`/`+` field diff, filters kept in the URL.
7. **Tests:** a catalog query fails if any data table lacks the trigger; a rolled-back write leaves no event; a write while the worker is down appears once it restarts; access is Admin-only; search and diff output.

**At scale:** monthly range partitions on `occurred_at` with a retention policy, and `eos_activity` moved to its own server (a connection-string change).

## Signed requests from Next.js to FastAPI: about 2 to 3 hours

**Goal:** prove that every API request came from our own Next.js server unaltered, and that every response came back unaltered; shut out anything that can reach port 8000 without the secret.

1. **Keys:** a secret of at least 32 random bytes in the environment of `web` and `api` only (never in the browser). At boot each process derives two keys with HKDF-SHA256, one per direction, so a captured request signature can never pass as a response signature. Keys sit in a small in-memory cache by key id, which allows rotation (old and new id side by side). The process refuses to start with a missing or short secret.
2. **Requests:** the server-side API client (`lib/api/server.ts`, which every Server Component and Server Action already uses) signs `v1`, method, path with sorted query, timestamp, a 128-bit nonce and the body's SHA-256, sent as `X-EOS-Key-Id`, `X-EOS-Timestamp`, `X-EOS-Nonce` and `X-EOS-Signature`. The browser-facing `/api` proxy becomes a route handler using the same client.
3. **Verification in FastAPI** (middleware, before routing): constant-time comparison, a timestamp within 60 seconds of the real clock (not `APP_NOW`), and a single-use nonce (`SET NX EX 120` in Redis, with a per-worker fallback if Redis is down). Any failure is `401 signature_invalid` with no hint about which part failed.
4. **Responses:** signed over status, the request's nonce, a timestamp and the body hash, so a valid response can't be swapped onto another request; the web server rejects a bad one as `502`. Each live (SSE) event carries its own signature.
5. **Exempt:** `/healthz`, `/docs`, `/redoc`, `/openapi.json`.
6. **Tests:** shared test vectors generated by Python and checked by both the Python and the TypeScript suites; missing, wrong-key, tampered-body, skewed and replayed requests all `401`; a tampered response becomes `502`.

**What it does not buy:** privacy (that needs TLS or mTLS) or user authentication (the session cookie and the access policy still run on every request). That is also why it ranked last: Altri's bonus list doesn't ask for it, and inside one Docker network it mostly protects against a misconfigured port, which the default `127.0.0.1` binding already covers.
